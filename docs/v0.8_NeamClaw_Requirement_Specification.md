## 1. Executive Summary

### 1.1 Purpose

Neam v0.8 introduces **NeamClaw** — a distinct agent type system that combines
**session-level control** (inspired by OpenClaw) with **process-level control** (inspired by
the Ralph Loop pattern) into first-class, type-safe language constructs. NeamClaw provides
two dedicated agent keywords — `claw agent` and `forge agent` — plus six composable traits,
enabling Neam agents to operate across a spectrum of execution modes with compile-time safety.
From persistent, always-on personal assistants to stateless, iteration-driven autonomous
coding agents — all within a single compiled DSL with the security guarantees of Neam's
v0.6.9 agentic security infrastructure.

### 1.2 The Core Insight

OpenClaw and Ralph represent two complementary control philosophies. NeamClaw gives each
its own dedicated type, rejecting invalid combinations at compile time:

```
  +-------------------------------------------------------------------+
  |                                                                   |
  |  claw agent: "Keep the agent alive, move the world through it"    |
  |  - Session persists, context accumulates                          |
  |  - Channels, heartbeat, compaction                                |
  |  - Best for: assistants, chatbots, real-time workflows            |
  |                                                                   |
  |  forge agent: "Keep the world alive, move the agent through it"   |
  |  - Process resets, filesystem is memory                           |
  |  - Verification, checkpoint, iteration                            |
  |  - Best for: coding agents, TDD, long-horizon tasks              |
  |                                                                   |
  |  agent: "Stateless request handler" (unchanged from v0.7.2)       |
  |  - Single .ask() call, no lifecycle                               |
  |  - Backward compatible with all existing Neam programs            |
  |                                                                   |
  |  NeamClaw: "The developer chooses — the compiler enforces"        |
  |  - Type-safe agent lifecycle management                           |
  |  - Invalid field combinations rejected at compile time            |
  |  - Both types share memory, security, and orchestration           |
  |                                                                   |
  +-------------------------------------------------------------------+
```

### 1.3 What NeamClaw Adds to Neam

| Capability | Before (v0.7.2) | After (v0.8 NeamClaw) |
|------------|-----------------|----------------------|
| Agent types | Single `agent` keyword, stateless | 3 types: `agent`, `claw agent`, `forge agent` |
| Execution | Single `.ask()` call | Persistent sessions (claw) OR iterative loops (forge) |
| Type safety | Runtime mode string | Compile-time type validation |
| Composability | None | 6 built-in traits (`Schedulable`, `Sandboxable`, etc.) |
| Memory | None between calls | 3-tier: session, workspace, semantic |
| Context management | Full context per call | Fresh context (forge) or managed compaction (claw) |
| Multi-channel | HTTP API only | Channels (Telegram, Slack, Discord, CLI, HTTP) |
| Concurrency | Thread pool per request | Lane queues with serial/parallel control |
| Drift prevention | None | Checkpoint + verify + fresh-context loops |
| Multi-agent | Sequential pipeline | Spawn, delegate, supervise, DAG orchestration |
| Proactive behavior | None | `impl Schedulable` — heartbeat + cron |
| Tool sandboxing | Bash metachar rejection | `impl Sandboxable` — per-execution Docker sandbox |

### 1.4 Key Metrics

- **3 agent types**: `agent` (stateless), `claw agent` (session), `forge agent` (loop)
- **6 composable traits**: `Schedulable`, `Channelable`, `Sandboxable`, `Monitorable`, `Orchestrable`, `Searchable`
- **3 memory tiers**: session history, workspace files, semantic search
- **4 lane types**: main, subagent, cron, custom
- **7 channel adapters**: HTTP, CLI, Telegram, Slack, Discord, Webhook, Cron
- **10 security domains**: Inherited from v0.6.9, extended with sandbox policies
- **13 new opcodes**: `OP_DEFINE_CLAW_AGENT`, `OP_DEFINE_FORGE_AGENT`, workspace/memory/spawn/verify/compact/flush ops

## 2. Problem Statement & Motivation

### 2.1 The Agent Lifecycle Gap

Neam v0.7.2 agents are **stateless request handlers**. Each `.ask()` call is independent —
there is no conversation history, no persistent memory, no lifecycle management. This limits
Neam to single-turn Q&A and prevents the following use cases:

| Use Case | Requirement | Current Gap |
|----------|-------------|-------------|
| Personal assistant | Multi-turn conversation with memory | No session persistence |
| Coding agent | Iterate until tests pass | No loop/verify construct |
| Workflow automation | React to events in real-time | No channel/heartbeat system |
| Chatbot | Serve multiple users simultaneously | No session isolation |
| Research agent | Long-horizon with drift protection | No checkpoint/verify cycle |
| TDD agent | External verification drives completion | No verify callback |

### 2.2 Why Not Just Use OpenClaw or Ralph Directly?

| Limitation | OpenClaw | Ralph |
|-----------|----------|-------|
| Language | TypeScript (430K LoC) | Bash (~100 lines) |
| Compilation | Interpreted | N/A |
| Type safety | Runtime checks only | None |
| Security | Prompt-based (bypassable) | `--dangerously-skip-permissions` |
| Tool governance | Config-based allowlists | None |
| Cost management | None | Token/cost limits only |
| Deployment | Self-hosted Node.js | Local bash |
| Agent definition | Markdown files (AGENTS.md) | Markdown files (PROMPT.md) |

NeamClaw brings these patterns into a **compiled, type-safe, security-hardened DSL** where:
- Agent behavior is defined in `.neam` source, not loose markdown files
- **Agent types are enforced at compile time** — a `forge agent` cannot have `channels`, a `claw agent` cannot have `verify`
- Security policies are enforced by the compiler and VM, not prompt instructions
- Memory management is handled by the runtime, not the developer
- Deployment is handled by existing Neam generators (Docker, K8s, Lambda)
- Cost tracking is built into the budget system

### 2.3 The Neam Advantage

Neam already has infrastructure that neither OpenClaw nor Ralph possess:

| Neam Feature | NeamClaw Leverage |
|-------------|-------------------|
| v0.6.6 Native tool calling | Skills become NeamClaw tools with schema validation |
| v0.6.7 External skills (MCP/HTTP) | NeamClaw inherits full MCP + HTTP tool ecosystem |
| v0.6.8 Sandboxed bash | Forge agents get sandboxed execution for free |
| v0.6.9 Agentic security (10 domains) | Claw + forge agents inherit audit, policy, injection defense |
| v0.7.0 Data types | Rich data processing within agent loops |
| v0.7.1 OOP (struct/trait/sealed) | Agent traits (`impl Schedulable for X`) reuse OOP infrastructure |
| v0.7.2 HotVM | Claw agents reuse warm VMs; forge agents use fresh VMs from pool |
| Budgets | All agent types enforce cost/token/time limits |
| Guards | All agent types pass tool I/O through guard chains |
| Deploy generators | NeamClaw agents deploy to Docker/K8s/Lambda unchanged |

## 3. Prior Art Analysis

### 3.1 OpenClaw — Session-Level Control

**Architecture**: Hub-and-spoke gateway (Node.js/TypeScript, 430K LoC) centered on a
WebSocket control plane. Channel adapters normalize messages from 15+ platforms into a
common format. The Agent Runtime assembles context (system prompt + memory + history),
invokes the LLM, executes tool calls, and persists state.

**Key Innovations**:

1. **Lane Queue System**: Default-serial, explicit-parallel concurrency. Each session gets
   a lane; tasks within a lane execute serially to prevent state corruption. Only idempotent
   tasks (cron, background checks) move to parallel lanes.

2. **Three-Tier Memory**: Session history (JSONL transcripts), workspace memory (curated
   Markdown files like MEMORY.md), and semantic search (SQLite with hybrid vector+BM25).

3. **Compaction**: When context approaches model limits, a pre-compaction flush tells the
   agent to write important facts to disk, then older conversation is summarized. The LLM
   context is treated as a cache; disk memory is the source of truth.

4. **Heartbeat System**: Proactive agent behavior — every N minutes, the gateway sends a
   heartbeat; the agent checks for pending tasks and either acts or stays silent.

5. **Tool Policy Stack**: 7-layer permission chain from global policy down to per-session
   sandbox policy. Deny always wins.

6. **Multi-Agent Routing**: Multiple agents share one gateway, each with isolated workspace,
   skills, sessions, and channel bindings.

**Strengths**: Rich multi-channel support, persistent identity, proactive behavior, mature
memory system, production-grade observability.

**Weaknesses**: Security relies heavily on prompt instructions (bypassable via injection),
context rot over long sessions despite compaction, 430K LoC TypeScript complexity,
self-hosted Node.js dependency.

**Use Cases**: Personal assistants, real-time workflow automation, messaging/chatbots,
interactive tool orchestration, multi-turn decision making.

### 3.2 Ralph Loop — Process-Level Control

**Architecture**: A bash loop that spawns fresh AI agent instances per iteration. State
persists exclusively through the filesystem (git commits, progress files, PRD JSON).
The loop script is the outer controller — it can terminate and restart agents at will.

**Core Loop**:
```bash
while :; do cat PROMPT.md | claude-code --continue; done
```

**Key Innovations**:

1. **Fresh Context Per Iteration**: Each iteration starts with a clean context window.
   The agent reads current filesystem state, performs one task, commits, and terminates.
   No context rot, no attention dilution.

2. **Git as Checkpoint**: Every successful task results in a `git commit`, providing
   full history, revert capability, and diff visibility for the next iteration.

3. **External Verification**: The agent does not decide if it succeeded — test suites,
   linters, and build systems do. A `verifyCompletion` callback checks objective criteria.

4. **File-Based State**: `IMPLEMENTATION_PLAN.md` tracks task status, `AGENTS.md`
   accumulates learnings, `progress.txt` logs iteration history. These files are the
   shared state between otherwise isolated iterations.

5. **Double-Loop Architecture**: Inner loop (LLM tool calling) handles implementation;
   outer loop (bash/verify) handles iteration and convergence.

6. **Drift Prevention**: Fresh context eliminates semantic drift. Small task granularity
   prevents coordination drift. External verification prevents behavioral drift.

**Strengths**: Eliminates context rot, deterministic lifecycle, minimal complexity (~100
lines), strong drift prevention, TDD-native, cost-efficient.

**Weaknesses**: No multi-channel support, no persistent identity, no real-time capability,
requires `--dangerously-skip-permissions`, no built-in security.

**Use Cases**: Coding and repository agents, test-driven development agents, long-horizon
tasks with drift risk, evaluation-driven research.

### 3.3 Comparative Analysis

```
                    Session Control          Process Control
                    (OpenClaw)               (Ralph Loop)
                    ──────────────           ──────────────
  Context Model     Accumulated +            Fresh per iteration
                    compaction

  Memory Location   In-session + disk        Filesystem only
                    (JSONL + Markdown +       (git + .md + .json)
                     SQLite vectors)

  Drift Risk        Medium (compaction       Low (fresh context
                    is lossy)                 eliminates drift)

  Multi-Channel     15+ platforms            None (single process)

  Multi-Agent       Built-in spawn/          External orchestration
                    delegate                 (separate project)

  Convergence       Single-pass or           Eventual consistency
                    manual retry              via iteration

  Security          Prompt-based +           None (--skip-permissions)
                    config allowlists

  Proactivity       Heartbeat + cron         None (triggered by loop)

  Best For          Assistants, chatbots,    Coding, TDD, research,
                    automation, workflows     long-horizon tasks

  Complexity        430K LoC TypeScript      ~100 lines bash
```

## 5. Design Principles

### 5.1 Type-Safe Agent Declarations

The execution model is determined by the **agent type keyword**, not a runtime string.
The developer writes `claw agent X { ... }` or `forge agent X { ... }`, and the compiler
validates field compatibility and generates appropriate bytecode. Invalid combinations
(e.g., `channels` on a forge agent, `verify` on a claw agent) are rejected at compile time.

### 5.2 Shared Security Infrastructure

All agent types inherit Neam's v0.6.9 security domains. There is no "unsafe mode" — even
forge agents execute within policy, audit, and injection defense boundaries. This
is the critical advantage over Ralph's `--dangerously-skip-permissions`.

### 5.3 Memory Is External, Context Is Managed

Following Ralph's insight: the filesystem is the source of truth, the LLM context is
a cache. NeamClaw provides language-level primitives for managing this distinction
(workspace files, memory search, compaction, flush).

### 5.4 Compilation Over Configuration

Where OpenClaw uses JSON config files and Ralph uses markdown files, NeamClaw uses
compiled `.neam` source. Agent behavior, tool policies, memory rules, and verification
logic are all part of the program — type-checked, optimized, and deployable.

### 5.5 Composable Traits Over Monolithic Features

Agent capabilities are composed through traits (`impl Trait for AgentType`), reusing
Neam's v0.7.1 OOP trait system. This avoids feature bloat in agent declarations and
enables per-agent opt-in to capabilities like scheduling, sandboxing, and monitoring.

### 5.6 Minimal Blast Radius

Security decisions are made at the narrowest possible scope. Per-session tool policies,
per-lane concurrency limits, per-iteration sandboxing, and per-agent budget enforcement
ensure that a compromised agent cannot escalate beyond its boundaries.

## 6. Agent Type System

### 6.1 Agent Type Hierarchy

NeamClaw defines three agent types with distinct keywords:

```
                        +---------------+
                        |    agent      |    (stateless — unchanged from v0.7.2)
                        |  .ask() only  |
                        +-------+-------+
                                |
                +---------------+---------------+
                |                               |
        +-------+-------+              +-------+-------+
        |  claw agent   |              | forge agent   |
        |  (session)    |              | (loop)        |
        +---------------+              +---------------+
```

| Keyword | Name | Inspiration | Purpose |
|---------|------|-------------|---------|
| `agent` | Stateless Agent | Neam v0.7.2 | Single `.ask()` call, no lifecycle, backward compatible |
| `claw agent` | Claw Agent | OpenClaw (session-level) | Persistent sessions, multi-turn, multi-channel, compaction, heartbeat |
| `forge agent` | Forge Agent | Ralph Loop (process-level) | Fresh context per iteration, verification-driven, git checkpoints |

### 6.2 Common Fields (All Agent Types)

| Field | Type | Description |
|-------|------|-------------|
| `provider` | String | LLM provider ("openai", "ollama", "bedrock") |
| `model` | String | Model identifier |
| `system` | String | System prompt |
| `skills` | List | Skill references |
| `guardchains` | List | Guard chain references |
| `budget` | Identifier | Budget reference |
| `policy` | Identifier | Security policy reference |
| `workspace` | String | Workspace directory path |

### 6.3 Claw Agent Specific Fields

| Field | Type | Description | Required |
|-------|------|-------------|----------|
| `session` | Object | Session config (idle_reset_minutes, compaction, etc.) | Yes |
| `channels` | List | Channel adapter references | Yes |
| `lanes` | Object | Lane queue configuration | No (defaults provided) |
| `semantic_memory` | Object | Semantic search config (backend, search mode) | No |
| `connected_knowledge` | List | Knowledge base references | No |

**Compile-time rejection**: `verify`, `checkpoint`, `loop` fields on a claw agent produce a compiler error.

### 6.4 Forge Agent Specific Fields

| Field | Type | Description | Required |
|-------|------|-------------|----------|
| `loop` | Object | Loop config (max_iterations, max_cost, etc.) | Yes |
| `verify` | Function | Verification callback returning VerifyResult | Yes |
| `checkpoint` | String | Checkpoint strategy ("git", "snapshot", "none") | No (default: "git") |

**Compile-time rejection**: `session`, `channels`, `lanes` fields on a forge agent produce a compiler error.

### 6.5 The Six Composable Traits

Traits extend agent capabilities using Neam's v0.7.1 `impl Trait for Type` syntax:

| Trait | Purpose | Primary Target | Required Methods |
|-------|---------|----------------|------------------|
| `Channelable` | Multi-channel message routing | claw agents | `fn channels(self)`, `fn on_message(self, msg)` |
| `Schedulable` | Heartbeat + cron scheduling | claw agents | `fn on_heartbeat(self)`, `fn heartbeat_interval(self)`, `fn on_cron(self, id)` |
| `Sandboxable` | Docker sandbox per execution | both | `fn sandbox_config(self)` |
| `Monitorable` | Behavioral monitoring + anomaly detection | both | `fn on_anomaly(self, event)`, `fn baseline(self)` |
| `Orchestrable` | Spawn/delegate sub-agents | both | `fn on_spawn(self, child)`, `fn on_delegate(self, result)` |
| `Searchable` | Semantic memory search | both | `fn search_config(self)`, `fn on_index(self, doc)` |

### 6.6 Syntax Examples

**Claw agent with traits:**
```neam
claw agent PersonalAssistant {
  provider: "openai",
  model: "gpt-4o",
  system: "You are a helpful personal assistant.",
  session: { idle_reset_minutes: 120, compaction: "auto" },
  channels: [TelegramChannel, HttpChannel],
  workspace: "./pa_workspace",
  semantic_memory: { backend: "sqlite", search: "hybrid" },
  skills: [Calendar, Email, WebSearch],
  budget: PersonalBudget
}

impl Schedulable for PersonalAssistant {
  fn on_heartbeat(self) {
    let pending = workspace_read("tasks/pending.md");
    if (pending.len() > 0) { return HeartbeatAction.Notify(pending); }
    return HeartbeatAction.Silent;
  }
  fn heartbeat_interval(self) { return 30; }
}
```

**Forge agent with traits:**
```neam
forge agent TDDCoder {
  provider: "openai",
  model: "gpt-4o",
  system: "Write tests FIRST, then implement.",
  loop: { max_iterations: 30, max_cost: 15.00 },
  verify: fun(ctx) {
    let r = exec("npm test", timeout: 120000);
    return r.exit_code == 0
      ? VerifyResult.Done("Tests pass")
      : VerifyResult.Retry(r.stderr);
  },
  checkpoint: "git",
  workspace: "./my_project",
  skills: [BashTool, FileEditor, GitTool]
}

impl Sandboxable for TDDCoder {
  fn sandbox_config(self) {
    return { mode: "always", network: "disabled", allowed_commands: ["npm", "node", "git"] };
  }
}
```

**Stateless agent (unchanged from v0.7.2):**
```neam
agent SimpleHelper {
  provider: "openai",
  model: "gpt-4o",
  system: "You are helpful.",
  skills: [WebSearch]
}
```

### 6.7 Trait Compatibility Matrix

| Trait | `agent` | `claw agent` | `forge agent` |
|-------|---------|-------------|--------------|

## 8. Session-Level Control (Claw Agents)

### 8.1 Session Lifecycle

```
  CREATE          ACTIVE           COMPACTING         RESETTING
    |                |                  |                  |
    |  First msg     |  Messages        |  Context full    |  Daily/idle
    |  from channel  |  accumulate      |  Flush + shrink  |  reset trigger
    |                |  Tools execute   |                  |
    |                |  Memory grows    |                  |
    +------>---------+-------->---------+-------->---------+
                     ^                                     |
                     |            Archive old session      |
                     +---<--- Create new session ID -------+
```

**States**:
- **Created**: New session for a session-key (claw agent + channel + peer)
- **Active**: Receiving messages, executing tools, persisting history
- **Compacting**: Context approaching limit; flushing memory, summarizing old turns
- **Resetting**: Creating a new session ID (daily reset, idle timeout, or manual `/reset`)
- **Archived**: Old session transcript preserved on disk for audit

### 8.2 Session Key Format

```
claw:<agent_id>:<channel_type>:<scope>:<identifier>
```

Examples:
- `claw:assistant:http:main` — Main HTTP session
- `claw:assistant:telegram:dm:+1234567890` — Telegram DM
- `claw:assistant:slack:group:#engineering` — Slack group channel
- `claw:assistant:cron:daily_digest` — Isolated cron session

### 8.3 Session Storage

Sessions are stored as append-only JSONL files under the claw agent's workspace:

```
<workspace>/sessions/
  sessions.json           # Session key -> session ID index
  <session_id>.jsonl      # Append-only transcript
  <session_id>.jsonl.bak  # Archived previous transcripts
```

Each JSONL line contains:
```json
{
  "type": "message|tool_call|tool_result|system",
  "id": "<uuid>",
  "parent_id": "<uuid>",
  "timestamp": "2026-02-16T10:30:00Z",
  "role": "user|assistant|tool",
  "content": "...",
  "metadata": { "channel": "telegram", "sender": "+1234567890" }
}
```

### 8.4 Context Assembly

On each turn, the claw runtime assembles context from multiple sources:

```
System Prompt (from claw agent declaration)
  + Workspace identity files (AGENTS.md, if exists)
  + Workspace memory (MEMORY.md, loaded in private sessions only)
  + Semantic search results (relevant past context)
  + Tool definitions (from skills, filtered by policy)
  + Session history (recent turns, within token budget)
```

### 8.5 Compaction Strategy

When assembled context exceeds 80% of the model's context window:

1. **Pre-compaction flush**: The agent is given a silent turn: "You are about to lose
   context. Write anything important to workspace memory files now."
2. **Agent writes** to MEMORY.md or daily log via workspace_write skill
3. **Compaction**: Older conversation turns are summarized into a `branch_summary` entry
4. **Recent turns** remain intact
5. If compaction itself would exceed limits, **session reset** is triggered

### 8.6 DM and Group Policies

| Policy | Behavior |
|--------|----------|
| `open` | Anyone can message the agent |
| `allowlist` | Only listed identifiers receive responses |
| `pairing` | Unknown senders receive a pairing code; must be approved |
| `mention_only` | In groups, agent only responds when @mentioned |

## 9. Process-Level Control (Forge Agents)

### 9.1 Loop Lifecycle

```
  INIT              ITERATE            VERIFY             CONVERGE
    |                  |                 |                   |
    |  Load plan       |  Fresh VM       |  Run tests/       |  All tasks
    |  Load prompt     |  Select task    |  linters/build    |  verified
    |  Load progress   |  Implement      |                   |
    |                  |  Git commit     |  Pass? -> next    |
    |                  |                 |  Fail? -> retry   |
    +-------->---------+-------->--------+-------->----------+
                       ^                 |
                       |  Inject feedback |
                       +----<------------+
```

### 9.2 Fresh Context Model

Each iteration is a **new VM instance** (leveraging v0.7.2 HotVM):

1. A fresh `VirtualMachine` is acquired from the `VMPool`
2. Bytecode is loaded from `BytecodeCache` (AOT-compiled)
3. The `__iteration__`, `__workspace__`, and `__task__` globals are injected
4. The agent executes with full attention budget on the current task
5. After execution, the VM is returned to the pool via `reset_for_reuse(Complete)`

This eliminates context rot by design — the forge agent never accumulates stale context.

### 9.3 Plan File Format

```json
{
  "project": "auth-feature",
  "stories": [
    {
      "id": "S1",
      "title": "Create user model",
      "status": "done",
      "completed_at": "2026-02-16T10:00:00Z",
      "iteration": 3
    },
    {
      "id": "S2",
      "title": "Implement login endpoint",
      "status": "in_progress",
      "started_at": "2026-02-16T10:05:00Z"
    },
    {
      "id": "S3",
      "title": "Add JWT token generation",
      "status": "open",
      "depends_on": ["S2"]
    }
  ]
}
```

### 9.4 Verification Callbacks

The `verify` function is called after each iteration. It receives the iteration context
and must return a `VerifyResult`:

```neam
verify: fun(ctx) {
  // Run the test suite
  let test_result = exec("pytest tests/", timeout: 120000);
  if (test_result.exit_code != 0) {
    return VerifyResult.Retry(f"Tests failed:\n{test_result.stderr}");
  }

  // Run linter
  let lint_result = exec("ruff check .", timeout: 30000);
  if (lint_result.exit_code != 0) {
    return VerifyResult.Retry(f"Lint errors:\n{lint_result.stdout}");
  }

  // Check if the specific file was created
  if (!file_exists("src/auth/login.py")) {
    return VerifyResult.Retry("login.py not yet created");
  }

  return VerifyResult.Done("All checks pass");
}
```

### 9.5 Stop Conditions

The forge loop terminates when any of these conditions is met:

| Condition | Source |
|-----------|--------|
| All stories `done` | Plan file |
| `max_iterations` reached | Forge agent `loop` declaration |
| `max_cost` exceeded | Budget tracker |
| `max_tokens` exceeded | Budget tracker |
| `verify` returns `Abort` | Verification callback |
| Manual SIGTERM/SIGINT | Graceful shutdown (v0.7.2) |

### 9.6 Checkpoint Strategies

| Strategy | Behavior |
|----------|----------|
| `"git"` | `git add -A && git commit` after each successful verification |
| `"snapshot"` | Copy workspace to `<workspace>/.snapshots/<iteration>/` |
| `"none"` | No automatic checkpointing (developer manages state) |

### 9.7 Learnings Accumulation

After each iteration, the forge controller appends to the learnings file:

```markdown
## Iteration 5 (2026-02-16 10:15:00)
- Task: S2 — Implement login endpoint
- Status: Completed
- Key decisions: Used bcrypt for password hashing, JWT RS256 for tokens
- Gotcha: SQLAlchemy session must be closed after each request
```

The next iteration reads this file, giving the fresh forge agent accumulated wisdom without
accumulated context noise.

## 10. Unified Memory Architecture

### 10.1 Three-Tier Memory Model

```
  +------------------------------------------------------------------+
  |  Tier 1: SESSION HISTORY                                         |
  |  - Append-only JSONL transcript                                   |
  |  - Per-session isolation                                          |
  |  - Auto-compacted when context is full                            |
  |  - Loaded into LLM context on each turn                           |
  |  Claw agents: always active                                       |
  |  Forge agents: N/A (fresh context per iteration)                  |
  |  Stateless agents: N/A                                            |
  +------------------------------------------------------------------+
  |  Tier 2: WORKSPACE FILES                                         |
  |  - Markdown files in agent workspace directory                    |
  |  - MEMORY.md: curated long-term facts                             |
  |  - memory/YYYY-MM-DD.md: daily running log                        |
  |  - plan.json, progress.md, AGENTS.md (forge agents)               |
  |  - Loaded selectively into context                                |
  |  Claw agents: MEMORY.md loaded in private sessions                |
  |  Forge agents: plan + prompt + progress loaded every iteration    |
  +------------------------------------------------------------------+
  |  Tier 3: SEMANTIC SEARCH                                         |
  |  - SQLite database with vector + BM25 index                       |
  |  - Indexes all .md files in workspace                             |
  |  - Hybrid search: 70% vector similarity + 30% keyword             |
  |  - Auto-reindexes on file changes (debounced)                     |
  |  - Queried via memory_search() built-in                           |
  |  - Enabled via `impl Searchable` or `semantic_memory:` field      |
  |  All agent types: available when configured                        |
  +------------------------------------------------------------------+
```

### 10.2 Memory Built-in Functions

| Function | Description |
|----------|-------------|
| `workspace_read(path)` | Read a file from the agent's workspace directory |
| `workspace_write(path, content)` | Write/overwrite a file in the workspace |
| `workspace_append(path, content)` | Append to a workspace file |
| `memory_search(query, top_k)` | Semantic search across workspace .md files |
| `session_history(session_key, limit)` | Read another session's transcript |
| `flush(target)` | Write current important context to a workspace file |

### 10.3 Memory Isolation Rules

| Context | MEMORY.md | Daily Log | Semantic Search | Session History |
|---------|-----------|-----------|-----------------|-----------------|
| Private DM (claw) | Loaded | Today + yesterday | Active | Full |
| Group chat (claw) | NOT loaded | NOT loaded | Read-only | Full |
| Cron job (claw) | Loaded | Today only | Active | Isolated session |
| Forge iteration | N/A | N/A | Available | N/A (fresh) |
| Subagent | NOT loaded | NOT loaded | Available | Own session |

## 12. Lane Queue System

### 12.1 Design: Default Serial, Explicit Parallel

NeamClaw adopts OpenClaw's lane queue philosophy: **serial by default** to prevent race
conditions, with explicit parallel lanes for safe concurrent work. Lanes are configured
inline on claw agents via the `lanes:` field.

### 12.2 Lane Types

| Lane | Default Concurrency | Purpose |
|------|-------------------|---------|
| `main` | 1 | Inbound messages, primary processing |
| `subagent` | 4 | Spawned child agents |
| `cron` | 2 | Scheduled background jobs |
| `heartbeat` | 1 | Proactive heartbeat checks |
| Custom lanes | Configurable | Developer-defined |

### 12.3 Queuing Semantics

```
  Message arrives for claw agent session S1
    |
    v
  Session lane: session:S1 (concurrency 1)
    |
    v
  Global lane: main (concurrency cap from config)
    |
    v
  Claw agent runtime processes the turn
    |
    v
  Lane slot released
```

- **Only one active run per session** (prevents state corruption)
- **Global concurrency cap** across all sessions (prevents resource exhaustion)
- **Immediate typing indicators** when supported by channel (UX feedback while queued)
- Messages arriving during processing can **steer** the current turn (cancel pending
  tool calls at the next tool boundary, inject as follow-up)

### 12.4 Lane Configuration in Claw Agents

```neam
claw agent Assistant {
  // ...
  lanes: {
    main: { concurrency: 1 },
    background: { concurrency: 4, priority: "low" },
    cron: { concurrency: 2 }
  }
}
```

**Note**: Lanes are claw-agent-only. Forge agents do not use lanes — each iteration
is a single-threaded execution with fresh context.

## 13. Checkpoint and Convergence

### 13.1 Claw Agents: Compaction as Convergence

In claw agents, convergence means maintaining coherent long-term behavior
despite context limits. The compaction cycle ensures this:

1. Context grows with each turn
2. At 80% capacity, pre-compaction flush saves critical state to disk
3. Older turns are summarized (lossy but controlled)
4. MEMORY.md and daily logs provide non-lossy persistent memory
5. Semantic search enables retrieval of arbitrarily old context

### 13.2 Forge Agents: Iteration as Convergence

In forge agents, convergence means eventually completing all tasks to an
externally verifiable standard:

1. Each iteration tackles one task with fresh context
2. Verification callback provides objective pass/fail
3. Failed verification injects feedback into the next iteration
4. Git commits create rollback points
5. Plan file tracks completion across iterations
6. Learnings file accumulates knowledge without accumulating noise

### 13.3 Convergence Guarantees

| Property | Claw Agent | Forge Agent |
|----------|-----------|-------------|
| Context freshness | Degrades, mitigated by compaction | Always fresh |
| State durability | JSONL + workspace files | Filesystem + git |
| Rollback | Session reset (new ID) | `git revert` to any commit |
| Drift detection | Behavioral monitor (v0.6.9 D9) | External verification |
| Drift prevention | Memory flush + compaction | Fresh context per iteration |

## 15. Security Integration

### 15.1 Leveraging v0.6.9 Agentic Security

NeamClaw inherits all 10 security domains from v0.6.9, extended for the distinct agent
types:

| Domain | v0.6.9 Capability | NeamClaw Extension |
|--------|------------------|-------------------|
| D1: Audit Log | 21 event types, 3 sinks | +Claw session events, +forge iteration events, +channel events |
| D2: Tool Policy | Allow/deny per skill | +Per-session policy, +per-channel policy, +per-lane policy |
| D3: Injection Scanner | Prompt injection detection | +Channel message scanning, +workspace file scanning |
| D4: Network Policy | SSRF protection | +Per-sandbox network rules, +channel allowlists |
| D5: Rate Limiter | Token bucket + sliding window | +Per-session rate limits, +per-channel rate limits |
| D6: Credential Manager | Secure storage + rotation | +Per-agent credential isolation, +sandbox key injection |
| D7: MCP Hardening | Hash pinning, timeout | Unchanged (MCP skills work in all agent types) |
| D8: Input Validation | Schema-based | +Channel message validation, +plan file schema validation |
| D9: Behavioral Monitor | Baseline + anomaly detection | +Cross-iteration drift detection (forge agents via `impl Monitorable`) |
| D10: Human-in-the-Loop | `sensitive: true` + confirmation | +Channel-specific approval flows, +forge iteration approval |

### 15.2 Claw Agent Security

```neam
// Security policy for claw agents
policy AssistantPolicy {
  // Tool permissions by channel context
  allow: ["web_search", "calculator", "file_read"],
  deny: ["bash_execute", "file_delete"],

  // Elevated permissions for private DMs only
  when_private: {
    allow: ["file_write", "workspace_write"]

  // Restricted in group chats
  when_group: {
    deny: ["file_read", "file_write", "workspace_write"],
    allow: ["web_search", "calculator"]

  // Sandbox configuration (also available via impl Sandboxable)

    mode: "non_main",
    tools_allowed: ["bash", "file_read", "file_write"],

    memory_limit: "512M"
```
```neam
  }
}
```

### 15.4 Security Advantages Over Prior Art

| Threat | OpenClaw Mitigation | Ralph Mitigation | NeamClaw Mitigation |
|--------|-------------------|------------------|---------------------|
| Prompt injection | Constitutional memory (bypassable) | None | Injection scanner (D3) — compile-time + runtime |
| Tool escalation | Config allowlists | `--skip-permissions` | Compiled policy stack (D2) — enforced by VM |
| Data exfiltration | PII filter gateway | None | Network policy (D4) + audit log (D1) |
| Credential theft | Local file permissions | None | Credential manager (D6) — encrypted + rotated |
| Runaway agent | None | Iteration limits | Budget (cost/token/time) + `impl Monitorable` (D9) |
| Context poisoning | Compaction | Fresh context | Both (compaction for claw + fresh context for forge) |
| Malicious skills | VirusTotal scanning | None | SHA-256 pinning (D7) + `impl Sandboxable` (D2) |
| Multi-agent manipulation | N/A | N/A | Per-agent policy isolation + HITL (D10) |
| Invalid config | Runtime errors | N/A | Compile-time type validation (field rejection tables) |

## 17. Runtime & VM Changes

### 17.1 New Object Types

| ObjType | Description |
|---------|-------------|
| `OBJ_CLAW_AGENT` | Claw agent definition (session config, channels, lanes, semantic memory) |
| `OBJ_FORGE_AGENT` | Forge agent definition (loop config, verify callback, checkpoint strategy) |
| `OBJ_CHANNEL` | Channel adapter (type, config, connection state) |
| `OBJ_VERIFY_RESULT` | Verification result (Done/Retry/Abort) |
| `OBJ_WORKSPACE` | Workspace handle (path, memory index) |
| `OBJ_LANE` | Lane queue (concurrency, pending items, active count) |
| `OBJ_LOOP_CONTEXT` | Forge loop iteration context (iteration #, task, feedback) |

**Removed from original spec**: `OBJ_SESSION` and `OBJ_HEARTBEAT` are no longer separate
object types. Session state is internal to `OBJ_CLAW_AGENT`; heartbeat is handled by the
`Schedulable` trait implementation stored in the trait registry.

### 17.2 VM Extensions

The `VirtualMachine` class gains:

```cpp
// Claw agent registry
std::unordered_map<std::string, ObjClawAgent*> claw_agents_;

// Forge agent registry
std::unordered_map<std::string, ObjForgeAgent*> forge_agents_;

// Trait implementations (reuses v0.7.1 trait system)
// impl_tables_ already stores trait impls per type

// Workspace
std::string workspace_path_;
MemoryIndex* memory_index_{nullptr};

// Channel routing (for claw agents)
std::vector<ChannelAdapter*> channels_;

// Lane queues (for claw agents)
LaneQueueEngine lane_engine_;

// Forge loop state (for active forge execution)
ForgeLoopContext* current_forge_loop_{nullptr};
int forge_iteration_{0};
```

### 17.3 New Native Functions

| Function | Signature | Description |
|----------|-----------|-------------|
| `workspace_read` | `(path: String) -> String` | Read file from workspace |
| `workspace_write` | `(path: String, content: String) -> Bool` | Write file to workspace |
| `workspace_append` | `(path: String, content: String) -> Bool` | Append to workspace file |
| `memory_search` | `(query: String, top_k: Number) -> List` | Semantic search |
| `session_history` | `(key: String, limit: Number) -> List` | Read session transcript |
| `spawn` | `(agent: String, config: Map) -> String` | Spawn sub-agent |
| `exec` | `(cmd: String, timeout: Number) -> Map` | Execute command (sandboxed) |
| `glob` | `(pattern: String) -> List` | Glob filesystem |
| `file_exists` | `(path: String) -> Bool` | Check file existence |

### 17.4 HotVM Integration

Claw agents use `VMPool` with `ResetPolicy::Standard` (preserve globals,
clear per-request state). Forge agents use `ResetPolicy::Complete` (full reset
for fresh context). Both leverage `BytecodeCache` for zero-cost agent loading.

### 17.5 Method Dispatch

| Agent Type | Primary Method | Description |
|------------|---------------|-------------|
| `agent` | `.ask(query)` | Single stateless query (unchanged) |
| `claw agent` | `.ask(query)` | Send message to active session |
| `forge agent` | `.run(config)` | Start forge loop, returns `LoopOutcome` |

## 20. Bytecode & Opcode Changes

### 20.1 New Opcodes

| Opcode | Operands | Description |
|--------|----------|-------------|
| `OP_DEFINE_CLAW_AGENT` | config_idx | Define a claw agent (session + channels + lanes) |
| `OP_DEFINE_FORGE_AGENT` | config_idx | Define a forge agent (loop + verify + checkpoint) |
| `OP_DEFINE_CHANNEL` | config_idx | Define a channel adapter |
| `OP_WORKSPACE_READ` | — | Pop path, push file content |
| `OP_WORKSPACE_WRITE` | — | Pop path + content, write file |
| `OP_MEMORY_SEARCH` | — | Pop query + top_k, push results |
| `OP_SPAWN_AGENT` | — | Pop agent name + config, spawn sub-agent |
| `OP_FORGE_ITERATE` | — | Start next forge loop iteration |
| `OP_VERIFY` | — | Run forge verification callback |
| `OP_COMPACT` | — | Trigger claw session compaction |
| `OP_FLUSH` | — | Flush memory to workspace |
| `OP_SESSION_HISTORY` | — | Pop key + limit, push history |
| `OP_FORGE_RUN` | — | Start forge agent loop, push LoopOutcome |

### 20.2 Estimated Opcode Count

Current: 103 opcodes (v0.7.2)
New: +13 opcodes
Total: ~116 opcodes

### 20.3 Stack Layout Differences

**OP_DEFINE_CLAW_AGENT** stack:
```
[session_config, channels_list, lanes_config, semantic_memory_config, agent_base_config]
```

**OP_DEFINE_FORGE_AGENT** stack:
```
[loop_config, verify_fn, checkpoint_strategy, agent_base_config]
```

This separation ensures that claw-specific and forge-specific data are never mixed at
the bytecode level, providing an additional layer of type safety.

## 21. Compiler Validation

### 21.1 Field Presence Rejection Table

The compiler rejects invalid field combinations at compile time:

| Field | `agent` | `claw agent` | `forge agent` |
|-------|---------|-------------|--------------|
| `provider` | OK | OK | OK |
| `model` | OK | OK | OK |
| `system` | OK | OK | OK |
| `skills` | OK | OK | OK |
| `guardchains` | OK | OK | OK |
| `budget` | OK | OK | OK |
| `policy` | OK | OK | OK |
| `workspace` | OK | OK | OK |
| `session` | Error | **Required** | Error |
| `channels` | Error | **Required** | Error |
| `lanes` | Error | OK | Error |
| `semantic_memory` | Warning | OK | OK |
| `connected_knowledge` | Warning | OK | OK |
| `loop` | Error | Error | **Required** |
| `verify` | Error | Error | **Required** |
| `checkpoint` | Error | Error | OK |

### 21.2 Required Field Enforcement

| Agent Type | Required Fields |
|------------|----------------|
| `agent` | `provider`, `model`, `system` |
| `claw agent` | `provider`, `model`, `system`, `session`, `channels` |
| `forge agent` | `provider`, `model`, `system`, `loop`, `verify` |

Missing required fields produce a compiler error:

```
Error [E081]: forge agent 'Coder' is missing required field 'verify'
  --> coding_agent.neam:5:1
  |
5 | forge agent Coder {
  | ^^^^^^^^^^^^ forge agents require a 'verify' callback
  |
  = help: add a verify field: verify: fun(ctx) { return VerifyResult.Done("ok"); }
```

### 21.3 Trait Compatibility Validation

The compiler validates trait implementations against agent types:

```
Error [E082]: trait 'Channelable' cannot be implemented for forge agent 'Coder'
  --> coding_agent.neam:20:1
  |
20 | impl Channelable for Coder {
   | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^ Channelable is only valid for claw agents
   |
   = help: forge agents do not support channels; use a claw agent instead
```

### 21.4 Deprecation Warnings

The `mode:` field (from spec v1.0) produces a deprecation warning with migration guidance:


## 24. Backward Compatibility

### 24.1 Existing Agents Continue to Work

All existing Neam agents (v0.6.2 through v0.7.2) that use the `agent` keyword without
`claw` or `forge` prefix default to **stateless mode** — the current behavior where each
`.ask()` call is independent. No existing programs break.

### 24.2 New Keywords

The following new keywords are reserved:

| Keyword | Construct |
|---------|-----------|
| `claw` | Prefix for claw agent declaration |
| `forge` | Prefix for forge agent declaration |
| `session` | Session configuration block (claw agent field) |
| `channel` | Channel adapter declaration |
| `workspace` | Agent workspace path |
| `verify` | Verification callback (forge agent field) |
| `spawn` | Spawn sub-agent |
| `compact` | Trigger compaction |
| `flush` | Flush memory |
| `dag` | DAG orchestration block |

These keywords must be accepted as parameter names in `parse_skill_param` (existing
pattern from v0.6.7).

### 24.3 Deprecated Constructs

| Old Construct | Status | Migration Path |
|--------------|--------|----------------|
| `agent X { mode: "session" }` | Deprecated (warning) | Use `claw agent X { ... }` |
| `agent X { mode: "loop" }` | Deprecated (warning) | Use `forge agent X { ... }` |
| `heartbeat X { ... }` | Deprecated (warning) | Use `impl Schedulable for X { ... }` |
| `cron X { ... }` | Deprecated (warning) | Use `impl Schedulable for X { fn on_cron(...) }` |
| `lane X { ... }` | Deprecated (warning) | Use `lanes: { ... }` inside claw agent |
| `memory: { ... }` (on agent) | Deprecated (warning) | Use `semantic_memory: { ... }` |

### 24.4 Additive Changes

All v0.8 changes are additive:
- New opcodes added (no existing opcodes changed)
- New object types added (no existing types changed)
- New native functions added (no existing functions changed)
- New neam.toml sections added (existing sections unchanged)
- New API endpoints added (existing endpoints unchanged)
- New binaries added (`neam-forge`)
- New built-in traits added (6 traits)
- Deprecated constructs still compile (with warnings)

### 24.5 Syntax Change Summary

| Old (v1.0 spec) | New (v2.0 spec) |
|---|---|
| `agent X { mode: "session", ... }` | `claw agent X { ... }` |
| `agent X { mode: "loop", ... }` | `forge agent X { ... }` |
| `agent X { ... }` (no mode) | `agent X { ... }` (unchanged) |
| `heartbeat { agent: X, check: ... }` | `impl Schedulable for X { fn on_heartbeat(self) { ... } }` |
| `cron { schedule: "...", agent: X }` | `impl Schedulable for X { fn on_cron(self, id) { ... } }` |
| `lane MainLane { concurrency: 1 }` | `lanes: { main: { concurrency: 1 } }` inside claw agent |
| `loop X { task: "..." }` expression | `X.run({task: "..."})` |
| `memory: { backend: "sqlite" }` | `semantic_memory: { backend: "sqlite" }` |
| `neam-loop` CLI binary | `neam-forge` CLI binary |
